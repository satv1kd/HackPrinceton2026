# Tasks 13, 14, 15 — what landed and what it assumes

Branch: `feat/tasks-13-14-15`

These three were built before their prerequisite tasks existed, against the
interfaces the PRD specifies. Everything here is unit-tested in isolation;
nothing has been run end to end, because tasks 1–12 are not in the tree yet.
This file is the handoff: the seams, the assumptions, and what is left.

## What landed

### Task 14 — canonical phoneme inventory and symbol mapping

| File | What it is |
|---|---|
| `app/phonetics/inventory.py` | The 39-phoneme canonical inventory, articulatory features, phonotactic exemptions, alignment sentinels |
| `app/phonetics/mapping.py` | espeak-IPA → canonical, ARPAbet → canonical, tokenizer, `MAPPING_REVISION` |
| `tests/test_phonetics_inventory.py` | 36 tests |

**Canonical set: ARPAbet without stress digits** (the CMUdict inventory). The
reasoning is in the `inventory.py` docstring; briefly — the lexicon (Task 16)
is CMUdict and needs no conversion, the symbols are ASCII so they stay
greppable in `phrases.json` / `feedback.jsonl` / profile keys, and dropping
stress avoids splitting already-scarce per-phoneme counts.

Things other tasks can use directly:

- `DELETION` / `INSERTION` sentinels — **Task 19** (aligner) and **Task 20**
  (profile) should import these rather than spelling them separately.
- `feature_similarity(a, b)` — the articulatory similarity the PRD asks for in
  the "identity-heavy, feature-adjusted" prior. **Task 20.**
- `NO_WORD_INITIAL` / `NO_WORD_FINAL` + `allows_word_initial/final()` — the
  documented exemption list the coverage checker needs. **Task 17.**
  Currently `{NG, ZH}` initial and `{HH, W, Y}` final.
- `CANONICAL_TO_IPA` — display spellings for the coverage table (Task 17) and
  the coverage screen (Task 22).

Unknown symbols **raise** `UnknownPhonemeError`. This is deliberate and load
bearing: a silently dropped phone is indistinguishable from a deletion by the
speaker, which would teach the Task 20 profile that the user omits sounds they
actually produced.

### Task 15 — phoneme recognizer

| File | What it is |
|---|---|
| `app/phonetics/recognizer.py` | `PhonemeRecognizer`, `Wav2Vec2PhonemeBackend`, `read_pcm_wav` |
| `scripts/measure_phoneme_latency.py` | Latency harness with a `--budget` gate |
| `tests/test_phoneme_recognizer.py` | 23 tests |

```python
from app.phonetics.recognizer import PhonemeRecognizer

result = PhonemeRecognizer().recognize("data/audio/<phrase>/<sample>.wav",
                                       cache_id="<sample_id>")
result.phonemes          # ['AY', 'W', 'AA', 'N', 'T']  canonical
result.posteriors        # (frames, vocab) float32, or None
result.inference_sec     # per-clip latency
result.from_cache        # True on a cache hit
```

- **Injectable backend.** The model sits behind a `PhonemeBackend` protocol;
  `torch` and `transformers` are imported inside `load()`, so importing the
  phonetics package costs nothing. Task 13's send proxy and Task 17's coverage
  checker both import it, and neither should pay for a 1 GB dependency.
- **Cache** at `data/phonemes/<id>.json` + `<id>.posteriors.npy`, matching the
  PRD layout. Invalidated when the model name **or** `MAPPING_REVISION`
  changes. Bump `MAPPING_REVISION` in `mapping.py` whenever you correct a
  mapping, or stale wrongly-mapped sequences will keep feeding the profile.
- **`is_model_available()`** is there for Task 1's `/api/health`
  ("phoneme model loaded").

### Task 13 — contacts, send proxy, send buttons

| File | What it is |
|---|---|
| `app/stores/contacts.py` | `ContactStore`, validation, atomic writes |
| `app/api/send.py` | `GET /api/contacts`, `POST /api/send`, `GET /api/photon/health` |
| `static/js/send.js` | The send buttons for the result card |
| `static/send-harness.html` | Dev harness for the buttons (not part of the app) |
| `data/contacts.example.json` | Copy to `data/contacts.json` and edit |
| `tests/test_contacts_store.py`, `tests/test_send_api.py`, `tests/js/send.test.mjs` | 34 + 20 tests |

Wiring, for Task 1:

```python
from app.api.send import router as send_router
app.include_router(send_router)
```

And for `/api/health`, fold in `app.api.send.photon_health(client)`.

**Failure policy.** A *caller* mistake is an HTTP error (404 unknown contact,
422 empty text). A *downstream* failure — Photon down, timed out, Messages not
signed in — returns `200 {"ok": false, "error": "..."}`, so the button shows a
"failed" state instead of throwing. By that point the user has already been
understood; only the send failed, and that difference should be visible to
them. A broken `contacts.json` is the exception: it returns 500, because
rendering zero send buttons would hide a setup error.

**`GET /api/contacts` withholds raw handles** and returns a `handle_hint`
(`…4567`, `c…@example.com`) instead. The client sends by `contact_id`, so it
never needs the number, and a result card may be held up to a stranger at a
counter. If Task 10 turns out to need the full handle, add it explicitly
rather than widening the default.

## Assumptions you may need to correct

1. **Package root is `app/`**, with `app.phonetics`, `app.stores`, `app.api`.
   If Task 1 picks a different layout, these move as whole directories.
2. **`app/settings_bridge.py` is a temporary seam onto Task 1's config.** It
   prefers `app.config.settings`, then the environment, then a default.
   **Delete it once Task 1 lands** and import the real settings object. Keys
   used: `PHONEME_MODEL`, `PHONEME_MODEL_OFFLINE`, `PHONEME_CACHE_DIR`,
   `CONTACTS_PATH`, `PHOTON_SERVICE_URL`, `PHOTON_TIMEOUT_SEC`.
3. **Audio is already preprocessed.** `read_pcm_wav` requires 16 kHz mono
   16-bit PCM WAV and raises otherwise, naming Task 3 in the error. It uses
   the stdlib `wave` module, so the phonetics package needs no `soundfile` or
   `librosa`.
4. **Photon's HTTP contract is `POST /send {to, text} -> {ok, error?}`**, plus
   an optional `GET /health`. A 404 on `/health` is treated as reachable,
   since it still proves the process is listening. Task 12 owns everything
   behind that; if the shape changes, only `_photon_send` changes.
5. **The confirmation gate lives in the client.** `renderSendButtons` refuses
   to render unless `confirmed === true`, and fails closed on truthy-but-not-
   true values. The server cannot enforce this, because the feedback store
   (Task 6) owns confirmation state. If you would rather enforce it
   server-side, `POST /api/send` would need to take an `attempt_id` and
   consult the feedback store — a deliberate change to the PRD's API shape.

## Not done

- **Send buttons are not wired into a result card.** Task 10 owns the card;
  `renderSendButtons` is ready for it. `static/send-harness.html` shows the
  intended call and lets you look at the button states.
- **Real-model latency has not been measured.** `torch`/`transformers` are not
  installed here and the weights are ~1 GB. Run this on the demo machine
  before building Task 21 on top of it:
  ```bash
  python scripts/measure_phoneme_latency.py --budget 1.5 data/audio/
  ```
  This is the PRD's "measure latency early in Phase 4" step, and it is still
  outstanding. The checkpoint's **output symbol set, license and latency** all
  remain open questions; if its symbols are not espeak-IPA, only
  `ESPEAK_TO_CANONICAL` needs to change.
- **No `requirements.txt` entry.** Task 1 owns that file and I did not want to
  collide with it. Needed: `fastapi`, `uvicorn`, `httpx`, `numpy`, `pydantic`
  for tasks 13–14, plus `torch` and `transformers` for task 15's real backend.
- **`GET /api/health`** is Task 1's; this branch only supplies the Photon part.

## Running the tests

```bash
python -m pytest tests/ -q          # 113 tests, no torch required
node --test tests/js/send.test.mjs  # 20 tests, no npm install required
```

Both suites are dependency-light on purpose: the Python tests replace the
model with a fake backend and Photon with an `httpx.MockTransport`, and the JS
tests use a small DOM stub rather than jsdom.
